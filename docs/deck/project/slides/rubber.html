AGENT REVIEW

Agents check the code. People check the decision.

MECHANICAL FIXES

Let agent review clear them

  • Bugs and missed edge cases
  • Error handling, style, tests
  • Everything needed is in the diff

DESIGN DECISIONS

Keep a person on them

  • Is this the right change at all?
  • The right abstraction, the right reading of the ask
  • How it fits the other work in flight

An agent's approval says the code is correct. It can't say the change is right, because the intent isn't in the diff.

Agent review is real and worth having. It's good at the mechanical fixes: bugs, missed edge cases, error handling, style. Those are most of the volume, and everything needed to find them is in the diff in front of it. Let it clear them, so your reviewers aren't spending their attention there. What it can't judge is the decision behind the change. Is this the right thing to build? Is it the right abstraction? Did we read the requirement correctly? Does it collide with what someone else is doing this week? None of that is in the diff. It lives in the heads of people who know why the change exists and what else is going on. Those are the defects that cause outages, and CI doesn't catch them either: the tests were written from the same understanding as the code. The trap: an agent-approved change looks verified, so it skips the human queue. The dashboard says quality went up. It didn't; a few weeks later the change failure rate tells you. That's Goodhart's Law: approval counts can be satisfied cheaply, so they will be. So split the work: agents on the mechanical pass, a person on the decision. This is a way of thinking about review, not a measured study.
